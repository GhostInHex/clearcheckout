`PaymentSnapshot` binds order ID, revision, safe integer minor-unit amount, USD currency and the fixed demo merchant identity. `PaymentAttempt` has a request key and a discriminated state. Manual confirmation only advances to awaitingGesture. A separate server operation starts provider approval. SQLite immediate transactions and unique request, active-order and provider-identity indexes prevent duplicate approval and capture. Paid attempts continue to reserve their order. Completed demos remain separate and cannot start real payment attempts.

The service instantiates the payment repository and invalidates pending attempts within the order-update transaction. Edits and demo confirmation cancel pre-provider attempts. Approval-phase edits become unknown, since a provider request may already exist. Capturing and unknown attempts preserve their immutable snapshots across cart edits. Settlement applies to that original snapshot, never to the changed cart. A changed cart cannot start another payment while the old outcome is uncertain or paid. A new order is required after payment. Definitively failed evidence permits a new attempt.

Only the injected server-owned PaymentProvider adapter supplies evidence. Its private parser checks order, revision, amount, currency, merchant and provider identity before settlement. There is no HTTP evidence endpoint or payment UI. Strict command schemas reject receipt and outcome fields. Provider errors are discarded rather than logged or exposed.
